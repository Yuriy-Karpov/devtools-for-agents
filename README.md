# DevTools Skills для AI-агентов

Набор специализированных skills для AI-агентов, которые помогают системно
отлаживать и проверять веб-приложения в живом браузере. Для работы skills
используют локальный `chrome-devtools-mcp`, подключающий агента к Chrome,
Chromium и другим браузерам на базе Chromium через Chrome DevTools Protocol.

Это не просто копия или отдельная реализация `chrome-devtools-mcp`. MCP-сервер
уже входит в репозиторий как инструментальный слой. Основная ценность проекта —
готовые skills, которые задают агенту методику работы: когда обращаться к
браузеру, какие данные собирать, в каком порядке проводить диагностику и как
проверять результат после изменения кода.

Репозиторий содержит набор skills, локальный MCP runtime, конфигурацию и
установочные скрипты, адаптированные для каждого поддерживаемого AI-агента.

GitHub: [Yuriy-Karpov/devtools-for-agents](https://github.com/Yuriy-Karpov/devtools-for-agents)

## Зачем нужен проект

Само по себе подключение MCP предоставляет агенту инструменты браузера, но не
определяет надёжный сценарий их применения. Агенту всё ещё нужно понимать, когда
получать новый snapshot, как воспроизводить пользовательский сценарий, какие
данные консоли и сети сопоставлять, как проводить профильный аудит и чем
подтвердить исправление.

Skills из этого проекта добавляют такие рабочие сценарии поверх
`chrome-devtools-mcp`. Они помогают агенту сначала собирать факты из живого
браузера, затем делать выводы и после изменения кода повторять проверку.

С помощью этого проекта агент может:

- открывать страницы и управлять вкладками;
- нажимать элементы, заполнять формы и воспроизводить пользовательские сценарии;
- читать DOM и accessibility tree;
- анализировать ошибки консоли и сетевые запросы;
- делать скриншоты и проверять адаптивную вёрстку;
- запускать Lighthouse-аудиты;
- исследовать производительность и утечки памяти;
- повторно проверять приложение после внесения исправлений.

## Набор skills

В каждый дистрибутив входят пять специализированных skills:

| Skill | Назначение |
| --- | --- |
| `devtools` | Отладка интерфейса, DOM, консоли, сети, скриншоты и браузерная автоматизация |
| `devtools-accessibility` | Проверка семантики, ARIA, клавиатурной навигации, фокуса, форм и accessibility tree |
| `devtools-performance` | Анализ загрузки и runtime-производительности, Core Web Vitals, long tasks и performance traces |
| `devtools-memory` | Поиск утечек памяти, detached DOM nodes, retained objects и анализ heap snapshots |
| `devtools-seo` | Технический SEO-аудит отрендеренной страницы, metadata, canonical, robots и structured data |

Skills выбираются агентом по контексту задачи и используют общий локальный
MCP-сервер `devtools`. MCP выполняет операции в браузере, а skills определяют
правильный процесс исследования и критерии проверки.

### `devtools-performance`

Skill диагностирует загрузку страницы и задержки пользовательских взаимодействий
по данным Chrome performance trace. Он применяется для проверки LCP, INP, CLS,
long tasks, сетевых задержек, render-blocking ресурсов и performance-регрессий.
Lighthouse для performance-аудита не используется.

Порядок работы:

1. Фиксирует URL, сценарий, viewport, авторизацию, cache, CPU/network throttling
   и доступность CrUX.
2. Выбирает reload trace для загрузки или ручной trace для взаимодействия.
3. Готовит сопоставимое состояние cache и приложения перед каждым измерением.
4. Записывает baseline без сетевого ограничения и эквивалентный запуск на
   `Slow 4G`. Для количественного сравнения выполняет не менее трёх пар.
5. Анализирует только относящиеся к проблеме insights и связывает метрику с
   конкретным ресурсом, main-thread task, rendering/layout событием или input.
6. Для проблем LCP определяет LCP-элемент и ресурс, разбирает TTFB, resource load
   delay, resource load duration и element render delay, затем проверяет Network
   и rendered markup для подтверждения причины.
7. Формирует краткий вердикт, отделяет нормальные показатели от проблем и
   приоритизирует действия по влиянию на пользователя.
8. Проверяет исправление в тех же условиях и завершает trace, отключает network
   throttling и восстанавливает CPU-профиль.

> **Термины:** LCP — время появления основного видимого контента; INP — задержка
> реакции страницы на действия пользователя; CLS — величина неожиданных сдвигов
> элементов при загрузке; long tasks — задачи на main thread длительностью более
> 50 мс, которые блокируют интерфейс; сетевые задержки — время ожидания и передачи
> документов, API и статических ресурсов; render-blocking ресурсы — CSS, scripts
> или fonts, задерживающие первоначальную отрисовку; performance-регрессия —
> измеримое ухудшение производительности после изменения кода, конфигурации или
> зависимостей.

### `devtools-memory`

Skill помогает исследовать использование JavaScript-памяти в Chromium и находить
причины её устойчивого роста. Он нужен при подозрении на утечку памяти во вкладке
браузера, ошибках Out of Memory, накоплении detached DOM nodes, объектов,
обработчиков событий, строк или контекстов после повторяющихся пользовательских
действий.

`devtools-memory` не считает рост памяти сам по себе доказательством утечки.
Skill воспроизводит полный жизненный цикл объекта или интерфейса, сравнивает
состояние heap до действия, во время него и после ожидаемого освобождения, а
затем ищет цепочку удержания до конкретного владельца в приложении или runtime.
Такой подход помогает отличить настоящую утечку от прогрева приложения, ленивой
инициализации, ограниченного кэша, пула объектов и обычной работы сборщика
мусора.

В начале skill находится короткий операционный чеклист, позволяющий выполнить
диагностику без повторного чтения всех пояснений. Порядок работы:

1. Фиксирует страницу, воспроизводимый сценарий, состояния **A** и **B**, действие
   освобождения **B → A**, viewport, авторизацию, версию браузера и число
   повторений.
2. Выбирает разрешённый каталог для snapshots вне репозитория.
3. Проверяет доступность инструментов анализа heap snapshots до запуска длинного
   сценария. Расширенный анализ требует запуска MCP с флагом
   `--memoryDebugging=true` или его алиасом `--experimentalMemory`.
4. Прогревает исходное состояние **A** и сохраняет snapshot `baseline`.
5. Несколько раз выполняет переход **A → B → A** с одинаковыми входными данными
   и временем ожидания, затем сохраняет snapshot `target` в состоянии **B**.
6. Выполняет ожидаемое освобождение **B → A**, ждёт по тому же правилу и
   сохраняет snapshot `final`.
7. Сравнивает `baseline`, `target` и `final`: сначала общие размеры и классы
   объектов, затем добавленные и оставшиеся экземпляры.
8. Для подозрительных объектов исследует retainers, retaining paths, dominators
   и outgoing edges, пока не будет найден вероятный владелец удерживаемой памяти.
9. Проверяет отдельные гипотезы об объектах, удерживаемых detached DOM nodes,
   консолью, обработчиками событий или JavaScript-контекстами.
10. По decision tree отличает устойчивое накопление от warm-up, ограниченного
    кэша, пула объектов, delayed cleanup и неопределённости garbage collection.
11. Формирует вывод: утечка подтверждена, подозревается или не подтверждена.
12. Закрывает загруженные snapshots, сообщает об оставшихся файлах и называет
    минимальный следующий тест.

Минимальный сценарий должен проверять одно действие без посторонней активности.
Например, для поискового диалога: **A** — диалог закрыт, **B** — диалог открыт с
одним фиксированным запросом, **B → A** — запрос очищен и диалог закрыт. Навигация,
разные запросы и другие действия не смешиваются с этим экспериментом.

Утечка считается подтверждённой только тогда, когда связанные со сценарием
объекты остаются после ожидаемого освобождения и цепочка удержания указывает на
правдоподобного владельца. Один большой snapshot, временный рост heap или имя
класса без retaining path для такого вывода недостаточны.

При интерпретации skill различает `shallow size` — собственный размер объекта —
и `retained size` — память, которая может освободиться вместе с удерживающим её
владельцем. Retained sizes пересекающихся графов не суммируются.

Если comparison tools недоступны, skill не разбирает `.heapsnapshot` как обычный
JSON. Он либо сохраняет согласованный triplet для последующего разрешённого
анализа, либо возвращает результат с низкой уверенностью и предлагает перезапуск
MCP с `--memoryDebugging=true` или отдельно разрешённый анализ через Memlab.

Итоговый отчёт всегда содержит шесть разделов: область проверки, вывод, находки,
ограничения, артефакты и очистку, следующий шаг. Даже частичный анализ завершается
явным статусом очистки и минимальным действием для повышения уверенности.

> **Безопасность:** heap snapshot может содержать URL, строки страницы,
> пользовательские данные и токены. По умолчанию skill не сохраняет файлы
> `.heapsnapshot` в репозиторий, не анализирует чувствительный профиль без явно
> заданного разрешения и не публикует snapshots без отдельного согласия
> пользователя.

## Поддерживаемые агенты

Каждый каталог является самостоятельным дистрибутивом. Подробная инструкция по
установке, настройке браузера, проверке и удалению находится в `README.md`
внутри каталога выбранного агента.

| Каталог | Агент | Инструкция |
| --- | --- | --- |
| `codex/` | Codex app и Codex CLI | [Установка для Codex](codex/README.md) |
| `gigacode/` | GigaCode | [Установка для GigaCode](gigacode/README.md) |
| `qwencode/` | Qwen Code | [Установка для Qwen Code](qwencode/README.md) |
| `opencode/` | OpenCode | [Установка для OpenCode](opencode/README.md) |

Дистрибутивы содержат один и тот же набор специализированных skills, но
учитывают различия в форматах расширений, конфигурации MCP, расположении файлов
и способах установки у разных агентов. Используйте только каталог нужного
клиента и следуйте инструкции внутри него.

## Как начать

1. Клонируйте репозиторий:

   ```bash
   git clone https://github.com/Yuriy-Karpov/devtools-for-agents.git
   cd devtools-for-agents
   ```

   Или через SSH:

   ```bash
   git clone git@github.com:Yuriy-Karpov/devtools-for-agents.git
   cd devtools-for-agents
   ```

2. Откройте каталог нужного агента.
3. Выполните шаги из находящегося в нём `README.md`.
4. Перезапустите агента или создайте новую сессию, если этого требует
   соответствующая инструкция.

## Общие требования

- совместимый AI-агент из списка выше;
- Node.js версии, указанной в инструкции выбранного дистрибутива;
- Chrome, Chromium, Microsoft Edge, Yandex Browser или другой
  совместимый Chromium-браузер.

Если стандартный Chrome не используется, путь к браузеру можно указать через
переменную окружения `CHROME_DEVTOOLS_BROWSER_PATH`. Дополнительные варианты
настройки описаны в инструкции для каждого агента.
