# DevTools Performance

Анализировать производительность через MCP-сервер `devtools`. Перед первым
обращением к MCP прочитать соседний скилл [devtools](../devtools/SKILL.md) и
применять его правила подключения, управления страницей, snapshot и безопасности.
Здесь описаны только performance-специфичные действия.

Анализировать приложение в предоставленной пользователем среде. Не менять способ
сборки или запуска, не переключать build mode и не перезапускать приложение ради
аудита. Если особенности текущей среды могут влиять на performance, указать это
как гипотезу или limitation и предложить повторное измерение в production-like
среде. Отсутствие сведений о сборке не блокирует аудит.

## Область и входные данные

До измерения зафиксировать URL или выбранную страницу, точный сценарий загрузки
или взаимодействия, desktop/mobile и viewport, авторизацию, состояние cache,
CPU/network throttling и доступность CrUX. Выбирать разумные значения, если они не
меняют смысл теста, и указывать их в отчёте.

До серии выбрать и зафиксировать:

- `series CPU` — коэффициент измеряемой серии;
- `CPU source` — пользователь, проект, default или `unchanged`;
- `restore CPU` — действие после серии.

Для `series CPU`:

- использовать значение пользователя или проекта, если оно задано; это значение
  само по себе не означает, что тот же профиль был активен до аудита;
- для desktop по умолчанию использовать `cpuThrottlingRate: 1`;
- для mobile performance-сценария предпочитать предоставленный или калиброванный
  коэффициент целевого класса устройств; если он недоступен, использовать
  `cpuThrottlingRate: 4` как синтетический fallback, а не эмуляцию конкретного CPU;
- если mobile viewport нужен только как условие сценария без требования
  моделировать менее производительный CPU, не включать throttling автоматически.

Не менять CPU-профиль внутри сравнимой серии. Указывать коэффициент и способ его
выбора в отчёте. Не пытаться читать или угадывать недоступное исходное состояние
CPU. Если пользователь явно сообщил активный до аудита коэффициент, восстановить
его. Если throttling включил аудит, после серии установить
`cpuThrottlingRate: 1`. Если аудит CPU не изменял, не выполнять CPU reset.

Для взаимодействия также определить воспроизводимое начальное состояние: route,
данные, состояние компонента, selection/scroll и шаг, с которого начинается trace.
Перед каждым измерением восстанавливать это состояние. Не повторять необратимые
или внешне значимые действия без безопасной fixture либо явного разрешения
пользователя.

Для загрузки использовать reload trace, для взаимодействия — ручной trace без
reload, для сравнения — эквивалентные условия. Не использовать `lighthouse_audit`
как performance-аудит: закреплённый runtime исключает категорию performance и
направляет такие задачи в tracing.

До сравнения выбрать и зафиксировать cache-протокол. Использовать cold/cold только
при наличии надёжной очистки cache или отдельных чистых isolated-профилей перед
каждым trace. Иначе использовать warm/warm: перед каждым измеряемым загрузочным
trace выполнить эквивалентный немеряемый warm-up в соответствующем сетевом профиле.
Если одинаковое состояние cache обеспечить нельзя, выполнить диагностику
раздельно, не приписывать дельту только сети и явно указать ограничение.

Измерительная пара состоит из baseline без network throttling и эквивалентного
trace с `Slow 4G` через `emulate(networkConditions: "Slow 4G")`. Если пользователь
явно не ограничил аудит одним сетевым профилем, выполнять одну или несколько таких
пар. Между профилями менять только `networkConditions`; сохранять одинаковыми
viewport, CPU throttling, auth, сценарий, начальное состояние приложения и
объявленное состояние cache. Если пользователь запросил только один профиль,
выполнять только его, сохранять cleanup и не делать парных выводов.

После каждой пары или при любой ошибке выполнить обязательный cleanup. Если запись
была запущена и её завершение не подтверждено, сначала попытаться вызвать
`performance_stop_trace`. Затем отключить сетевое замедление вызовом `emulate` без
`networkConditions` и повторно применить управляемый аудитом `series CPU`, viewport
и другие нужные параметры эмуляции. После всей серии выполнить зафиксированный
`restore CPU`: вернуть явно сообщённый исходный коэффициент, установить
`cpuThrottlingRate: 1`, если CPU менял аудит, либо не вызывать CPU emulation, если
аудит его не менял. Не оставлять выбранную страницу с активным trace или в
throttled-состоянии; о неуспешном cleanup сообщать явно.

## Рабочий процесс

1. Открыть целевое состояние и подтвердить его свежим snapshot или screenshot.
2. Зафиксировать начальное состояние приложения, выбрать cold/cold или warm/warm
   cache-протокол, `series CPU`, `CPU source`, `restore CPU` и режим:
   - `paired` — baseline и `Slow 4G`; одна пара для диагностики или не менее трёх
     валидных пар для количественного сравнения/регрессии;
   - `single-profile` — только профиль пользователя; один trace по умолчанию для
     диагностики или не менее трёх для количественного сравнения/регрессии, без
     парных выводов.
   Явно заданное пользователем число имеет приоритет. Если оно меньше трёх,
   результат считать диагностическим, а не regression-grade.
3. В режиме `paired` для baseline каждой пары отключить network throttling через
   `emulate` без `networkConditions`, применить CPU-профиль и остальные параметры
   эмуляции, восстановить начальное состояние приложения и подготовить cache.
   Запустить trace с подходящими reload/auto-stop. Для взаимодействия отключить
   auto-stop, выполнить минимальный flow и вызвать `performance_stop_trace`.
4. В режиме `paired` для `Slow 4G` восстановить то же начальное состояние,
   применить `emulate(networkConditions: "Slow 4G")` с тем же CPU-профилем,
   эквивалентно подготовить cache и повторить trace. Независимо от результата
   выполнить обязательный cleanup.
5. В режиме `single-profile` выполнить только выбранный профиль с теми же
   правилами CPU, подготовки состояния/cache, записи trace и cleanup.
6. Зарегистрировать каждый trace с `run index`, номером пары или `n/a`, сетевым
   профилем, CPU-профилем, cache-протоколом, статусом валидности и возвращёнными
   insight set IDs. Невалидный trace не включать в статистику; заменять его
   дополнительным запуском только в пределах retry budget: не более одной
   дополнительной пары/trace для диагностики и не более двух для количественного
   режима. В `paired` единицей retry считать всю пару, в `single-profile` — один
   trace. Если одна и та же ошибка повторилась дважды, прекратить retries и вернуть
   частичный отчёт. Явный лимит пользователя имеет приоритет. Изучить summary всех
   валидных traces. Передавать в `performance_analyze_insight` только ID и имена
   insights соответствующего trace; не смешивать insight sets разных запусков.
7. Связать каждую важную метрику с цепочкой доказательств: resource timing,
   main-thread work, rendering, layout, third party или конкретный input. Если LCP
   существенен для запроса или итоговой оценки, выполнить причинную диагностику
   LCP ниже. Network, Console, snapshot, screenshot, `evaluate_script` и emulation
   использовать только как дополнительные доказательства.
8. Проверить сопоставимость traces. Не удалять выбросы без объяснения. Сравнивать
   cold с cold и warm с warm; между baseline и `Slow 4G` менять только
   `networkConditions`, сохраняя одинаковые viewport, CPU throttling, auth и
   сценарий.
9. Для сопоставимых повторов рассчитать медиану и разброс каждого сетевого профиля.
   Одиночный trace или одну пару обозначать диагностическими и не использовать как
   доказательство регрессии.
10. Приоритизировать улучшения по влиянию на пользователя и ожидаемому эффекту.
   Описать эквивалентный trace для проверки каждой рекомендации.
11. После всех запусков подтвердить остановку trace, отключение network throttling
    и выполнение зафиксированного `restore CPU`.

## Причинная диагностика LCP

Использовать этот flow, если LCP медленный, является главной целью оптимизации или
показывает существенный риск в проверенных условиях. Не выполнять все проверки
механически, если LCP явно не относится к запросу.

1. По summary trace зафиксировать значение LCP и возвращённые имена insights.
   Проанализировать `LCPBreakdown`, если он доступен, затем изучить только
   релевантные дополнительные insights: например, `DocumentLatency`,
   `LCPDiscovery` и `RenderBlocking`.
2. Определить LCP-элемент и его тип: image, text или video. Предпочитать сведения
   об элементе и ресурсе, уже возвращённые trace insight. Если их нет,
   использовать свежий snapshot или read-only запрос через `evaluate_script` к
   buffered entries типа `largest-contentful-paint`. Считать отсутствие сведений
   об элементе ограничением; не угадывать LCP по визуально крупнейшему элементу.
3. Для LCP с отдельным ресурсом найти точный URL через `list_network_requests` и
   изучить его с `get_network_request`. Установить время начала запроса,
   инициатор, priority при наличии, redirects, длительность передачи, caching и
   доступность ресурса из исходного документа. Не выдумывать transfer size или
   priority, если инструмент их не вернул.
4. Проверять rendered markup только для гипотез, поддержанных trace:
   `loading="lazy"` на фактическом LCP image, обнаружение CSS background,
   JS-created или hydration-delayed markup, отсутствующий или неэффективный
   preload, отсутствующий `fetchpriority`, render-blocking styles/scripts, font
   blocking для text LCP либо позднее отображение скрытого контента. Крупное
   изображение во viewport — только кандидат на LCP; не рекомендовать
   `fetchpriority="high"` без подтверждения фактического LCP-ресурса или
   измеренной проблемы discovery.
5. Связать bottleneck с доминирующей подчастью LCP и выбирать рекомендации только
   из соответствующей ветки:
   - **TTFB** — проверить document redirects, server response, доставку и caching
     документа. Не предлагать image compression как основное исправление.
   - **Resource load delay** — обеспечить более раннее обнаружение фактического
     LCP-ресурса. Предпочитать исходный HTML с `<img>` или `<picture>`; убрать lazy
     loading с LCP-элемента; использовать `fetchpriority="high"` для
     подтверждённого LCP image. Если раннее HTML discovery невозможно, особенно
     для CSS background, использовать точный image preload и убедиться, что он
     совпадает с реально запрашиваемым ресурсом.
   - **Resource load duration** — проверить bytes, responsive sizing, encoding,
     request redirects, origin/CDN latency и cache behavior. Рекомендовать WebP,
     AVIF, `srcset`, CDN или caching только при наличии соответствующего evidence.
   - **Element render delay** — проверить render-blocking CSS или fonts,
     synchronous script, long main-thread tasks, client rendering/hydration и
     изменения visibility. Не предполагать, что уменьшение image сократит эту
     задержку.
6. Сохранять полную разбивку времени в evidence. Доли помогают найти потенциал
   улучшения, но не являются performance budgets: большая доля небольшого общего
   времени может не оправдывать работу, а меньшая доля плохого результата всё ещё
   может быть существенной.
7. Проверить исправление эквивалентным trace с теми же route, viewport, auth,
   cache, CPU и network profile. Сравнить изменяемую подчасть и общий LCP, а также
   убедиться, что CLS и другие существенные метрики не ухудшились. Для
   количественных before/after выводов использовать сопоставимые повторные
   запуски.

## Правила интерпретации

- Различать lab trace и field data CrUX. Отсутствие CrUX не блокирует lab-аудит.
- Не объявлять корреляцию причиной. Непроверенную причину обозначать гипотезой и
  называть следующий тест.
- Не переносить один запуск или одну страницу на весь сайт.
- Не сравнивать разные cache, device, CPU или auth условия. Разные network
  conditions сравнивать только в запланированной паре baseline / `Slow 4G`, где
  сеть является единственной намеренно изменяемой переменной.
- Не объявлять дельту из несопоставимых cache-состояний эффектом network
  throttling. Одну пару traces считать диагностикой, а не количественным
  доказательством регрессии.
- Не сравнивать runtime traces с разными route, данными или состояниями компонента.
  Если начальное состояние нельзя воспроизвести, анализировать запуски раздельно и
  помечать причинный вывод гипотезой.
- Для INP-подобной проблемы воспроизводить конкретное реальное взаимодействие;
  load-only trace недостаточен. Lab trace подтверждает задержку измеренного input,
  но не является полевым INP страницы. Field INP указывать только по подходящим
  полевым данным, например CrUX, с учётом их URL/origin-гранулярности.
- Не придумывать product budget. Если budget не задан, помечать общие пороги как
  ориентиры, а не приёмочные критерии.
- Общие диапазоны LCP — good до 2,5 с включительно, needs improvement выше 2,5 с
  и до 4,0 с включительно, poor выше 4,0 с — являются field guidance Core Web
  Vitals. Lab trace может использовать их только как ориентир и не доказывает,
  что URL или origin проходит field metric. Для field-оценки нужны подходящие
  полевые данные с учётом их URL/origin-гранулярности.
- Не определять severity только значением метрики; учитывать влияние на целевой flow.

## Формат результата

Отвечать на языке текущего диалога пользователя с агентом. Явно заданный
пользователем язык имеет приоритет. Если язык не определён, смешан или требуется
fallback, отвечать на русском. Не переводить имена MCP-инструментов, параметры,
insight IDs, значения enum и другие технические идентификаторы.

Писать для читателя, которому сначала нужно понять, быстр ли измеренный сценарий,
что действительно плохо и что делать дальше. Начинать с результата; протокол
измерения и trace identifiers помещать ближе к концу. Не заставлять читателя
выводить итог из сырых метрик.

Использовать такой порядок:

1. **Вердикт** — одно-два предложения простым языком. Указать, здоров ли
   измеренный сценарий, требует внимания или имеет серьёзную проблему, и назвать
   главную причину. Ограничить вердикт проверенным сценарием. Если существенных
   проблем нет, сказать об этом прямо. Не называть результат хорошим или плохим
   только по общему порогу; явно отмечать, что порог является ориентиром, если
   product budget не задан.
2. **Коротко** — небольшой список или таблица пользовательски значимых метрик и
   их смысла. Разделить `Что хорошо` и `Что требует внимания`. Не представлять
   технически интересное наблюдение как проблему, если измеренного влияния на
   пользователя нет. Когда LCP является существенным finding, назвать LCP-элемент
   или ресурс и показать четыре подчасти при наличии; иначе не добавлять breakdown
   только ради полноты.
3. **Что делать** — упорядоченные конкретные действия. Помечать их как `сейчас`,
   `следующим` или `опционально` по измеренному влиянию и ожидаемому эффекту. Если
   срочных действий нет, сказать об этом перед опциональными улучшениями.
4. **Проблемы** — только существенные findings по убыванию severity. Оформлять
   каждый finding короткими маркированными строками: `Проблема`, `Влияние на
   пользователя`, `Evidence`, `Действие`, `Проверка`. Указывать severity и
   confidence раздельно словами; не использовать неоднозначные заголовки вроде
   `[medium][high]`.
5. **Условия теста** — URL, сценарий, viewport/device, auth, cache-протокол, тип
   trace, число запусков, baseline и `Slow 4G`, `series CPU`, `CPU source`,
   `restore CPU`, допущения и статус cleanup. Добавить компактную таблицу runs с
   `run index`, парой или `n/a`, network/CPU profiles, cache, валидностью,
   ключевыми метриками и insight set ID. Точные trace identifiers держать здесь,
   если они не являются прямым evidence finding.
6. **Ограничения** — только влияющие на интерпретацию или покрытие ограничения:
   отсутствующие field data, недостаточное число валидных запусков, недоступные
   состояния, нестабильность, неизвестное исходное состояние CPU, исчерпанный
   retry budget, неуспешный cleanup или невыполненные проверки.

Пропускать пустые разделы. Не требующие действий детали, например ожидаемый шум
Console или не блокирующая request chain, помещать в короткий раздел
`Дополнительные замечания`, а не смешивать с приоритетными проблемами.

Использовать `critical` только когда проблема блокирует ключевой flow или делает
его фактически непригодным. Для каждого существенного finding указывать
наблюдение, влияние на пользователя, evidence, confidence (`high`, `medium` или
`low`), рекомендацию и эквивалентный verification trace. Рекомендацию по LCP
связывать с измеренной доминирующей подчастью и подтверждённым элементом/ресурсом,
а не перечислять общие способы оптимизации изображений.

Предпочтительный шаблон finding:

```md
### Finding title

Severity: medium. Confidence: high.

- **Проблема:** ...
- **Влияние на пользователя:** ...
- **Evidence:** ...
- **Действие:** ...
- **Проверка:** ...
```

Предпочитать компактный отчёт повторению одного факта в вердикте, метриках,
finding и рекомендации. Для сопоставимых повторов отдельно указывать медиану и
разброс baseline и `Slow 4G`. Одиночный trace или пару обозначать
диагностическими, а не regression-grade.

## Ограничения и остановка

Вернуть частичный отчёт, а не выдуманный результат, если страницу или сценарий
нельзя воспроизвести, trace не записывается, flow блокирует dialog/crash или нет
нужных инструментов. Указать выполненные проверки, точное ограничение и минимальный
следующий шаг. Завершать аудит, когда сценарий выполнен в заданных условиях,
получены валидные traces, существенные выводы связаны с evidence и описан повторный
