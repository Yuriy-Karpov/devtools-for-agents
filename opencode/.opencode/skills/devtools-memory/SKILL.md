# DevTools Memory

Анализировать память браузера через MCP-сервер `devtools`. Считать соседний скилл
`devtools` контрактом подключения, управления страницей, snapshot и безопасности;
применять его правила без копирования.

## Область и входные данные

Зафиксировать URL или выбранную страницу, точный повторяемый сценарий, ожидаемый
lifecycle объектов, viewport, авторизацию и число повторов. До capture определить
разрешённое место хранения артефактов. По умолчанию не сохранять `.heapsnapshot` в
репозиторий.

Heap snapshot может содержать строки, URL, пользовательские данные и tokens.
Остановиться до capture чувствительного подключённого профиля, если пользователь
явно не включил эти данные в scope. Не публиковать и не передавать snapshot без
явного разрешения.

## Предусловия и инструменты

Для capture использовать `take_heapsnapshot`. Для анализа использовать
`get_heapsnapshot_summary`, `get_heapsnapshot_details`,
`get_heapsnapshot_class_nodes`, `get_heapsnapshot_retainers`,
`get_heapsnapshot_retaining_paths`, `get_heapsnapshot_dominators`,
`get_heapsnapshot_edges` и `close_heapsnapshot`.

До длинного сценария проверить доступность инструментов анализа. Они требуют флаг
runtime `--memoryDebugging=true`. Если доступен только `take_heapsnapshot`, делать
capture лишь когда это полезно и явно сообщать, что полный MCP-анализ невозможен.

## Рабочий процесс

1. Стабилизировать страницу и описать lifecycle, после которого подозрительные
   объекты должны освобождаться.
2. Создать baseline snapshot в разрешённом временном или выходном каталоге.
3. Несколько раз одинаково выполнить минимальный сценарий.
4. Дать завершиться асинхронной работе и garbage collection в доступной среде
   степени. Не заявлять о forced GC, если он фактически не выполнялся.
5. Создать post-scenario snapshot. При необходимости повторить цикл, чтобы
   отличить устойчивый рост от initialization или delayed cleanup.
6. Сравнить summary и aggregate details, найти классы и экземпляры с повторяемым
   удерживаемым ростом.
7. Для подозрительных nodes исследовать class nodes, retainers, retaining paths,
   dominators и edges до выявления правдоподобного владельца.
8. После анализа закрыть загруженные snapshots через `close_heapsnapshot` и
   сообщить пути оставшихся артефактов.

## Правила интерпретации

- Не считать один большой snapshot утечкой. Требовать повторяемого роста и evidence
  удержания после завершения ожидаемого lifecycle.
- Проверять cache growth, lazy initialization, pooling и delayed cleanup.
- Не считать имя класса достаточным доказательством причины.
- Неполную retaining chain обозначать подозрением и называть следующий capture или
  interaction для проверки.
- Различать retained size, количество объектов и видимые пользователю симптомы.
- Использовать `critical` только когда память блокирует или обрушает ключевой flow.

## Формат результата

Вернуть:

1. **Scope** — страница, сценарий, повторы, auth, среда и пути артефактов.
2. **Summary** — `confirmed`, `suspected` или `not confirmed` с краткой причиной.
3. **Findings** — по убыванию `critical`, `high`, `medium`, `low`, `info`.
4. **Evidence** — сравнение snapshots, class/node IDs, counts/sizes, retainers,
   retaining paths, dominators, edges и lifecycle steps.
5. **Recommendations** — направление исправления ownership/cleanup и повторный тест.
6. **Limitations** — недоступные инструменты, неопределённость GC, границы
   чувствительных данных или недостаток повторов.

Для каждого finding указать наблюдение, влияние, evidence, confidence (`high`,
`medium`, `low`), рекомендацию и способ проверки.

## Ограничения и остановка

Вернуть частичный отчёт, если инструменты анализа недоступны, capture не удался,
сценарий невоспроизводим или чувствительные данные вне scope. Указать выполненные
проверки, точное ограничение и минимальный следующий шаг. Подтверждать утечку только
при одновременном наличии повторяемого роста и доказанной retaining path.
